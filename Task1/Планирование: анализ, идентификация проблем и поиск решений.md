## Cуществующие и потенциальные проблемные места
1) Один инстанс каждого приложения
   В описании сказано, что каждое приложение имеет по одному инстансу. При этом нагрузка растёт, а после открытия API компанию «завалило заказами». Это значит:
      * нет горизонтального масштабирования;
      * при падении инстанса приложение фактически недоступно;
      * особенно опасно для MES API и CRM API, через которые проходят заказы и статусы.
2) Отсутствие реплики базы данных - нет разделения read/write-нагрузки.
   * отчёты, дашборды и списки заказов конкурируют с транзакционными операциями;
   * нет отказоустойчивости на уровне БД;
   * рост числа заказов и чтений по статусам будет ухудшать время ответа;
   * загрузка первой страницы MES уже тормозит, и одна из причин в перегруженной БД.
3) Отсутствие автотестов/недостаточное покрытие тестов. Ручное тестирование и слабая автоматизация тормозят релизы и увеличивают риск дефектов
4) MES засыпает CRM сообщениями, которая та не успевает обработать. Интеграция через RabbitMQ, вероятно, не справляется с потоком или реализована ненадёжно
5) Медленная первая страница MES. Вероятный признак плохих запросов, отсутствия нужных индексов и корректно настроенного кеширования
6) Отсутствие backpressure для внешнего API. После открытия API нагрузка резко выросла, но в описании нет ничего про ограничения на API.
7) Нет полноценной наблюдаемости: мониторинга бизнес-цепочки, алертов, трассировки сообщений. Что привело к:
   * росту времени обработки заказа;
   * накоплению очередей в RabbitMQ;
   * зависшим или потерянным сообщениям
   * рост ошибок интеграции.
8) CI/CD недостаточно зрелый для системы с высокой бизнес-критичностью. В dev-окружение деплой автоматизирован, но в release и production он выполняется вручную.
9) Команда может быть не сбалансирована под текущие риски системы. MES на C# — критичный компонент, через который проходят расчёт стоимости, список заказов и производственный поток. При этом в команде только один C#-разработчик. Это ограничивает скорость развития и исправления проблем в самом критичном контуре системы. 
10) MES совмещает слишком много обязанностей и содержит бутылочное горлышко в расчёте стоимости
    MES API одновременно:
    * показывает список заказов;
    * назначает заказы операторам;
    * рассчитывает стоимость заказа.

## Инициативы, которые необходимы для устранения нежелательных ситуаций
1) Необходимо развернуть все приложение в окружении kubernetes. Это позволит автоматизировать развёртывания и главное масштабирования
2) Настроить минимум одну реплику по модели master-slave
3) Настроить автотесты, увеличиить процент покрытия, не выпускать в релиз ошибки не только с высоким приоритетом 
4) Оптимизировать работу с RabbitMQ. Сделать дополнительные инстансы RabbitMQ, разделить очереди и провести другие настройки RabbitMQ или заменить на кафка - предложи что можно сделать лучше всего
5) Проанализировать запросы, оптимизировать запросы при надобности, настроить индексы, а также настроить кеширование по паттерну - предложить какой паттерн который больше подходит и почему
6) Настроить взаимодействие с внешним API через брокер RabbitMQ(или заменить его на Kafka) - реализовать паттерн Backpressure
7) Настроить мониторинг системы по модели "Четыре золотых сигнала" и трассировку запросов 
8) Коротко описать корректные этапы CI/CD
9) Стоит нанять сотрудника 
10) Разбить MES на меньшие части, особенно важно выделить расчет стоимости  


## Инициативы, которые необходимы для устранения нежелательных ситуаций
1. Стабилизировать поток заказов между системами и исключить потерю заказов.

Это самая приоритетная инициатива, потому что именно потерянные и «зависшие» заказы уже приводят к жалобам клиентов и потере контрактов.
Что нужно сделать:

* провести аудит текущей интеграции MES ↔ CRM ↔ Shop через RabbitMQ;
* внедрить гарантированную обработку сообщений:
    * retry;
    * dead-letter queue;
    * идемпотентность обработчиков;
    * корреляционные идентификаторы заказов;
    * контроль порядка обработки событий;
* реализовать сверку заказов между системами
* ввести бизнес-метрики:
    * сколько заказов создано;
    * сколько дошло до CRM;
    * сколько зависло на каждом статусе;
    * среднее время прохождения заказа по этапам.

Сейчас основной ущерб бизнесу наносит то, что заказы теряются или надолго застревают в процессе.

2. Выделить расчёт стоимости из MES в отдельный сервис

Сейчас MES совмещает несколько ролей: интерфейс для операторов, назначение заказов и расчёт стоимости. При этом расчёт цены — самая тяжёлая операция: от 2–3 минут до 30 минут в зависимости от сложности 3D-модели.

Что нужно сделать:

* вынести расчёт стоимости в отдельный сервис;
* обрабатывать расчёт асинхронно, через очередь задач;
* выделить отдельные воркеры под расчёт;
* масштабировать именно этот контур независимо от операторского интерфейса;
* хранить статус расчёта отдельно: queued, in_progress, completed, failed.

Пока расчёт стоимости живёт внутри MES, тяжёлые операции конкурируют за ресурсы с UI операторов и обработкой заказов. Это прямое бутылочное горлышко системы.

3. Ограничить и управлять входящим потоком заказов через внешний API

После открытия API нагрузка резко выросла, а архитектура оказалась к этому не готова. Значит, необходимо контролировать поток запросов и не пускать в систему больше заказов, чем она может переварить.

Что нужно сделать:

* внедрить rate limiting и квоты для внешних партнёров;
* добавить механизм backpressure:
    * если очередь расчёта или обработки превышает порог, API не принимает заказ синхронно;
    * клиент получает ответ, что заказ принят в обработку или временно отложен;
* перейти на модель, где внешний API публикует заказы в брокер, а не нагружает синхронно тяжёлые сервисы;
* при необходимости разделить очереди:
    * отдельная очередь для B2B;
    * отдельная очередь для B2C;
    * отдельная очередь для расчёта стоимости.

Система не должна падать под нагрузкой. Нужен управляемый приём нагрузки.

4. Усилить надёжность брокера сообщений и пересмотреть его роль в архитектуре

* настроить:
    * durable queues;
    * persistent messages;
    * DLQ;
    * retry policy;
    * prefetch limits;
    * отдельные очереди по типам событий;
* масштабировать consumers;

5. Оптимизировать чтение данных для MES: запросы, индексы и кэширование

Что нужно сделать:

* снять профилирование медленных запросов;
* проверить план выполнения SQL-запросов;
* добавить недостающие индексы, особенно по:
    * статусу заказа;
    * дате создания;
    * дате обновления;
    * назначенному оператору;
* использовать предрасчитанную таблицу / materialized view
* применить кэширование.

Здесь лучше всего подходит Cache-Aside.

* данные читаются часто, а изменяются относительно предсказуемо;
* паттерн простой в реализации и хорошо подходит для списков, фильтров, агрегатов и часто читаемых представлений.

Как это может выглядеть:

* при запросе дашборда приложение сначала проверяет кэш;
* если данных нет, получает их из БД и кладёт в кэш;
* устанавливается ttl на запись.

6. Масштабировать приложения и уйти от single point of failure

Сейчас у каждого приложения по одному инстансу, а это и узкое место по производительности, и точка отказа.

Что нужно сделать:

* перейти к запуску нескольких экземпляров каждого backend-сервиса;
* вынести приложения за балансировщик;
* масштабировать отдельно:
    * Shop API;
    * CRM API;
    * MES API;
    * сервис расчёта стоимости;
    * consumers очередей;
* обеспечить health checks и auto-restart.

На будущее рассмотреть Kubernetes 

7. Улучшить архитектуру БД и повысить отказоустойчивость

Одного инстанса БД недостаточно для растущей системы.

Что нужно сделать:

* настроить как минимум одну read replica;
* разделить read-heavy и write-heavy нагрузки;
* продумать резервное копирование и сценарии failover;
* при необходимости вынести аналитические запросы и тяжёлые выборки из основной транзакционной БД.

8. Настроить полноценную наблюдаемость системы

Сейчас команда узнаёт о проблемах в основном через жалобы пользователей. Это слишком поздно.

Что нужно сделать:

* внедрить мониторинг по модели четырёх золотых сигналов:
    * Задержка;
    * Трафик;
    * Ошибки;
    * Насыщенность;
* внедрить централизованные логи;
* добавить distributed tracing между Shop / CRM / MES / брокером;
* настроить алерты на:
    * рост очередей;
    * рост ошибок обработки сообщений;
    * превышение времени расчёта;
    * увеличение числа зависших заказов.

9. Повысить зрелость CI/CD и ускорить безопасный выпуск изменений

Сейчас процесс релизов сильно зависит от ручных действий и ручного тестирования.

Что стоит сделать:

* автоматизировать не только unit-, но и:
    * integration tests;
    * contract tests между сервисами;
    * smoke tests после деплоя;
    * критические E2E-сценарии;
* ввести обязательные quality gates;
* автоматизировать rollout в release-окружение;
* использовать:
    * feature flags;
    * canary deployment;
    * rollback strategy;
* сократить долю ручной регрессии.


10. Усилить команду в критичных местах

Сейчас MES — критичный контур, но C#-экспертиза сосредоточена почти в одном человеке. Также явно не хватает автоматизации тестирования.

Что стоит сделать:

* нанять ещё одного C# backend engineer;
* усилить QA-направление:
    * либо нанять QA automation engineer,
    * либо выделить время текущему QA на полноценную автоматизацию;
* при росте платформы рассмотреть усиление DevOps/SRE-направления.

Почему это нужно:

* снизится bus factor;
* критичный сервис перестанет зависеть от одного разработчика;
* автоматизация тестов и эксплуатация перестанут быть узким местом.


## Целевая архитектура через полгода

Через полгода целевая архитектура должна выглядеть примерно так:

На уровне приложений

* Shop API, CRM API и MES API работают в нескольких экземплярах за балансировщиком.
* Сервис расчёта стоимости вынесен отдельно и масштабируется независимо.
* Consumers очередей масштабируются отдельно от API.

На уровне интеграции

* RabbitMQ остаётся основным брокером, но используется корректно:
    * отдельные очереди по сценариям;
    * retry и DLQ;
    * идемпотентные обработчики;
    * outbox pattern для критичных событий.
* Внешний API принимает заказы управляемо:
    * rate limiting;
    * приоритеты;
    * асинхронная постановка в обработку.

На уровне данных

* Для транзакционных операций остаются основные БД.
* Для чтения и дашбордов используются:
    * read replica;
    * read model;
    * кэш;
    * предрасчитанные представления для MES.

На уровне эксплуатации

* Система развёрнута в управляемой среде, желательно в Kubernetes, если команда успеет подготовить приложения.
* Есть мониторинг, трассировка, алерты и дашборды по техническим и бизнес-метрикам.
* Есть автоматические smoke/integration/contract tests.
* Релизы проходят быстрее и безопаснее.
