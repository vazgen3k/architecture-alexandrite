# Мотивация

Сейчас компания узнаёт о проблемах в системе в основном постфактум: по жалобам клиентов, партнёров и операторов. Это означает, что команда не видит проблему в момент её возникновения, а реагирует уже тогда, когда бизнес понёс ущерб: заказ потерян, срок сорван, оператор не может взять заказ в работу, партнёр недоволен, а компания теряет выручку и контракты.

### Что даст мониторинг компании:
- Снижение потерь заказов и выручки
- Прозрачность всей цепочки обработки заказа
- Защита B2B-направления и репутации компании
- Сокращение времени реакции на инциденты

# Выбор подхода к мониторингу

### Комбинированный подход:

* для API — «Четыре золотых сигнала»;
* для очередей и MES дашборд— RED;
* для MES "просчет"(новый выделенный сервис) и CRM — USE.

### 1. Выделенный из MES сервис расчёта стоимости — подход USE

Сервис расчёта стоимости является одним из главных узких мест системы. Расчёт стоимости занимает в среднем 2–3 минуты, а в сложных случаях — до 30 минут. Значит, для него важно в первую очередь отслеживать именно использование и насыщение ресурсов.

Какие метрики нужно отслеживать

1. Загрузка CPU

Расчёт стоимости зависит от сложности 3D-модели. Метрика позволит понять, является ли CPU основным ограничением производительности.

Ярлыки:

* instance
* environment
* service
* calculation_type — если появятся разные типы расчётов
* model_complexity_bucket — например, small, medium, large

2. Использование памяти

Обработка сложных 3D-моделей может потреблять много памяти. Метрика поможет выявлять утечки памяти, неэффективную обработку больших файлов и риски OOM.

Ярлыки:
* instance
* environment
* service

⸻

3. Количество активных воркеров / занятых потоков

Если все воркеры заняты, новые задачи на расчёт будут ожидать в очереди, а время обработки будет расти.

Ярлыки:

* instance
* service

⸻

4. Длина очереди задач на расчёт

Показывает, сколько заказов ожидают расчёта. Это одна из ключевых метрик деградации сервиса.

Ярлыки:

* queue_name
* environment
* priority
* source — например, b2c или b2b

⸻

5. Время расчёта стоимости

Это ключевая бизнес- и техническая метрика. Нужна для контроля деградации сервиса и соблюдения SLA обработки заказов.

Ярлыки:
* service
* source
* model_complexity_bucket
* result — success / error

⸻

6. Количество ошибок расчёта

Помогает видеть, как часто сервис не может обработать модель, падает или возвращает некорректный результат.

Ярлыки:

* error_type
* instance
* source
* service

⸻


### 2. API системы — подход «Четыре золотых сигнала»

Применять к:

* Shop API
* CRM API
* MES API
* внешнему API для партнёров

Это основной способ контролировать доступность и качество интеграции.

Какие метрики нужно отслеживать

1. Latency — время ответа API

Показывает, насколько быстро система отвечает пользователям и партнёрам. Позволяет вовремя заметить деградацию.

Ярлыки:

* service
* endpoint
* method
* status_code
* environment
* client_type — web, crm, partner_api, operator_ui

⸻

2. Traffic — количество запросов

Показывает текущую нагрузку на API и помогает понимать, откуда приходит рост трафика.

ярлыки:

* service
* endpoint
* method
* client_type
* environment

⸻

3. Errors — количество и доля ошибочных запросов

Даёт понимание стабильности API

ярлыки:

* service
* endpoint
* method
* status_code
* error_type
* client_type

⸻

4. Saturation — насыщение ресурсов

Зачем нужна:
Показывает, насколько близок сервис к пределу своих возможностей. Полезно для выявления перегрузки до фактического отказа.

Ярлыки

* service
* instance
* resource_type — CPU, memory, DB connections, thread pool

⸻

### 3. Очереди сообщений — подход RED

Для RabbitMQ лучше использовать RED, потому что очередь — это поток событий, и здесь важно понимать:

* сколько сообщений проходит;
* сколько времени занимает обработка;
* сколько ошибок возникает.

Какие метрики нужно отслеживать

1. Rate — скорость поступления и обработки сообщений

Позволяет понять, успевают ли consumers обрабатывать входящий поток или очередь постепенно переполняется.

Ярлыки

* queue_name
* exchange
* producer_service
* consumer_service
* message_type
* source

⸻

2. Errors — количество ошибок обработки сообщений

Показывает, сколько событий не было обработано успешно, ушло на повторную попытку или в DLQ.

Ярлыки

* queue_name
* consumer_service
* message_type
* error_type
* retry_count

⸻

3. Duration — время обработки сообщения

Если время обработки растёт, это признак деградации consumers или зависимых сервисов.

Ярлыки

* queue_name
* consumer_service
* message_type
* result

⸻

### 4. MES-дашборд — подход RED

Для первой страницы MES, которую открывают операторы, удобнее всего использовать RED. Это пользовательский сценарий, и здесь важно измерять не столько инфраструктуру, сколько качество работы конкретной функции.

Какие метрики нужно отслеживать

1. Rate — количество открытий дашборда и запросов к нему

Позволяет понять, насколько активно используется страница и как растёт нагрузка в рабочие часы.

Ярлыки

* page
* user_role
* environment

⸻

2. Errors — ошибки загрузки страницы и виджетов

Помогает отслеживать, сколько запросов к дашборду завершается ошибкой и насколько это влияет на работу операторов.

Ярлыки

* page
* widget
* status_code
* error_type

⸻

3. Duration — время полной загрузки страницы

Это ключевая метрика пользовательского опыта операторов. По условию именно эта страница уже работает медленно.

Ярлыки

* page
* widget
* user_role
* result

⸻

### 5. CRM — подход USE

Для CRM можно использовать USE, если смотреть на неё как на внутреннюю рабочую систему продавцов и администраторов, где важна устойчивость ресурсов и способность обрабатывать операционные сценарии без деградации.

Но здесь есть важная оговорка:
для CRM API лучше использовать «Четыре золотых сигнала», а для самой CRM как прикладного контура и её инфраструктуры — USE.
То есть CRM фактически стоит мониторить двумя слоями.


Какие USE-метрики нужны для CRM

1. CPU utilization

Показывает, насколько загружен backend CRM и не упирается ли он в процессор при пиковых сценариях.

Ярлыки

* service
* instance
* environment

⸻

2. Память

Нужна для контроля утечек памяти и ухудшения работы приложения под нагрузкой.

Ярлыки

* service
* instance

⸻

3. Использование пула соединений к БД

Важная метрика для CRM, так как она работает с заказами, статусами и синхронизацией.

Ярлыки

* service
* db_name
* instance

⸻

4. Saturation по воркерам / thread pool

Показывает, не исчерпан ли ресурс обработки запросов и фоновых задач.

Ярлыки

* service
* instance
* pool_name

⸻

5. Ошибки на уровне зависимостей

Нужно видеть проблемы не только в самой CRM, но и в зависимостях: БД, очередях, внешних вызовах.

Ярлыки

* dependency
* error_type
* service

⸻

Дополнительные бизнес-метрики:

1. Количество заказов по каналам

Позволяет видеть реальный объём заказов по всем источникам: сайт, CRM, внешний API.

Ярлыки:

* source — b2c, b2b, crm_manual
* status
* environment

⸻

2. Время прохождения заказа между статусами

Это главная метрика для поиска бутылочных горлышек в бизнес-процессе.

Ярлыки:

* from_status
* to_status
* source
* result

⸻

3. Количество зависших заказов

Например, заказ находится в одном статусе дольше допустимого SLA. Позволяет выявлять реальные проблемные заказы до жалоб клиентов.

Ярлыки:

* status
* source
* sla_bucket

⸻

4. Количество заказов, потерянных между системами

Например:

* заказ есть в Shop, но нет в CRM;
* есть в CRM, но нет в MES;
* есть событие в очереди, но нет результата обработки.

Ярлыки:

* source_system
* target_system
* order_type

⸻

5. Количество заказов старше обещанного срока

Показывает уже прямое влияние технических проблем на выполнение обязательств перед клиентами.

Ярлыки:

* source
* delay_bucket
* status


## План действий

1. Развернуть базовую платформу мониторинга
    Поднять инфраструктуру для сбора, хранения и визуализации метрик, логов и трассировок.
    Например: time-series БД, система дашбордов, централизованный сбор логов и tracing.
2. Добавить мониторинг критичных компонентов системы
    Настроить сбор метрик для:
    * Shop API;
    * CRM API;
    * MES API;
    * RabbitMQ;
    * сервиса расчёта стоимости;
    * баз данных.
3. Добавить бизнес-мониторинг жизненного цикла заказа
    Начать отслеживать путь заказа через все системы:
    * количество заказов по каналам;
    * переходы между статусами;
    * время нахождения в статусах;
    * зависшие и потерянные заказы;
    * заказы с нарушением SLA.
4. Настроить централизованные логи, трассировку и алерты
    Обеспечить возможность быстро находить причину сбоя по конкретному заказу или запросу, а также настроить уведомления при превышении порогов по критичным метрикам.
5. Подготовить дашборды и регламенты реакции на инциденты
    Сделать отдельные дашборды для команды разработки и бизнеса, определить пороги, ответственных, правила эскалации и действия при деградации системы.
