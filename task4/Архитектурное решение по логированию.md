# Логирование системы


Логирование нужно настраивать для следующих компонентов:

* Shop API
* CRM API
* MES API
* RabbitMQ
* 3D files storage
* Shop DB и MES DB — на уровне технических и audit-логов

* Расчёт стоимости будет вынесен в отдельный сервис, его также нужно логировать отдельно.

⸻

Какие логи нужно собирать

Логи бизнес-событий заказа

Нужно логировать:

* создание заказа;
* отправку заказа;
* загрузку 3D-файла;
* расчёт стоимости;
* подтверждение производства;
* смену статуса заказа;
* назначение заказа оператору;
* начало и завершение производства;
* упаковку, отправку и закрытие заказа.

Для таких логов на уровне INFO нужно сохранять:

* время;
* order_id;
* customer_id или обезличенный идентификатор;
* source;
* предыдущий и новый статус;
* service;
* correlation_id;
* trace_id — если уже внедрён трейсинг;
* результат операции.

⸻

Логи интеграции

Нужно логировать:

* публикацию сообщения в RabbitMQ;
* получение сообщения consumer;
* подтверждение обработки;
* повторную попытку обработки;
* отправку сообщения в DLQ.

На уровне INFO:

* время;
* message_id;
* queue_name;
* message_type;
* order_id;
* correlation_id;
* trace_id;
* результат обработки;
* номер попытки.

⸻

Логи операций с 3D-файлами

Нужно логировать:

* загрузку файла;
* успешное сохранение;
* чтение файла для расчёта;
* ошибки доступа;
* удаление временных файлов.

На уровне INFO:

* время;
* file_id;
* order_id;
* размер файла;
* формат файла;
* результат.

⸻

Логи расчёта стоимости

Нужно логировать:

* старт расчёта;
* завершение расчёта;
* длительность;
* результат;
* постановку расчёта в очередь.

На уровне INFO:

* время;
* order_id;
* file_id;
* сложность модели;
* duration_ms;
* результат;
* рассчитанную цену.

⸻

Аудит-логи действий пользователей

Нужно логировать:

* вход в систему;
* открытие карточки заказа;
* ручное изменение статуса;
* подтверждение производства;
* назначение заказа оператору;
* ручное закрытие заказа.

На уровне INFO:

* время;
* user_id;
* роль пользователя;
* действие;
* order_id;
* результат.

⸻

Какие INFO-логи обязательны

Минимально обязательно логировать:

1. создание заказа;
2. отправку заказа;
3. загрузку 3D-файла;
4. старт и завершение расчёта стоимости;
5. публикацию сообщения в RabbitMQ;
6. получение сообщения из RabbitMQ;
7. смену статуса заказа;
8. назначение заказа оператору;
9. подтверждение производства;
10. ошибки интеграции и отправку в retry/DLQ.

⸻

Мотивация

Логирование нужно добавить, потому что сейчас система распределённая, а заказ проходит через несколько приложений, очередь сообщений, базы данных и файловое хранилище. Без логов невозможно быстро понять, где именно произошёл сбой и что случилось с конкретным заказом.

Логирование даст компании:

* историю событий по заказу;
* возможность расследовать потерянные и зависшие заказы;
* прозрачность интеграции между системами;
* аудит действий сотрудников;
* основу для алертинга и поиска аномалий.

Метрики, на которые повлияет внедрение логирования

Технические:

* MTTR;
* время диагностики инцидента;
* количество необъяснимых ошибок;
* количество автоматически найденных ошибок интеграции.

Бизнесовые:

* количество потерянных заказов;
* количество зависших заказов;
* доля заказов с нарушением SLA;
* количество жалоб от B2B-партнёров;
* среднее время прохождения заказа между статусами.

⸻

Что настраивать в первую очередь

Поскольку команда не может одновременно внедрить всё, в первую очередь логирование нужно настроить для:

1. MES API — самый критичный и перегруженный компонент;
2. CRM API — важен для подтверждения и синхронизации заказов;
3. RabbitMQ — здесь заказ может зависнуть или потеряться;
4. Shop API — точка входа B2C-заказов.

Трейсинг в первую очередь также нужно настраивать для:

* MES API;
* CRM API;
* Shop API;
* RabbitMQ-интеграции.

⸻

Предлагаемое решение

Для централизованного логирования предлагается использовать стек:

* Loki — хранение логов;
* Grafana — просмотр и анализ;
* Grafana Alloy — сбор логов;
* Prometheus — сбор метрик;
* Alertmanager — алерты.

⸻

Политика безопасности

* доступ к логам только для ролей Backend, DevOps, Support, Tech Lead;
* вход в Grafana через корпоративную учётную запись;
* production-логи доступны ограниченному кругу сотрудников;
* запрещено логировать пароли, токены, платёжные данные, содержимое 3D-файлов;
* чувствительные поля должны маскироваться;
* доступ к логам должен аудироваться;
* передача логов должна идти по защищённым каналам.

⸻

Политика хранения логов

* application logs — 30 дней;
* audit/security logs — 90–180 дней;
* debug-логи — 7–14 дней;
* отдельные потоки или индексы для:
    * shop-api
    * crm-api
    * mes-api
    * rabbitmq
    * security
    * audit
* старые логи при необходимости архивируются в более дешёвое хранилище.

⸻


Алертинг

Нужно настроить алерты на:

* рост ERROR-логов в MES API;
* появление сообщений в DLQ;
* рост ошибок расчёта стоимости;
* всплеск неуспешных вызовов внешнего API;
* рост ошибок доступа к 3D storage.

Поиск аномалий

Нужно отслеживать:

* резкий рост числа заказов;
* аномальный рост очереди;
* всплеск retry;
* падение числа событий перехода заказа между статусами;
* резкий рост ошибок после релиза;
* аномально большой поток запросов от одного API-клиента.
