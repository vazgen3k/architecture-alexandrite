Компоненты, которые необходимо покрыть трейсингом

1. Shop API
    Здесь заказ создаётся со стороны интернет-магазина, пользователь загружает 3D-файл и отправляет заказ. На этом этапе возможны:
    * ошибки создания заказа;
    * ошибки загрузки файла;
    * неполная запись данных в Shop DB;
    * разрыв цепочки между созданием заказа и дальнейшей обработкой.
2. CRM API
    CRM участвует в подтверждении заказа и синхронизации статусов. Здесь заказ может:
    * не появиться после поступления события;
    * зависнуть на этапе подтверждения;
    * не синхронизироваться со статусами MES.
3. MES API
    Это один из самых критичных узлов системы. Здесь происходят:
    * расчёт стоимости заказа;
    * показ списка заказов;
    * назначение заказов операторам;
    * смена производственных статусов.
        Именно здесь заказ может долго зависать или ломаться.
4. Messages Queue (RabbitMQ)
    Через очередь проходят сообщения о новых заказах и изменении статусов. Здесь возможны:
    * накопление сообщений;
    * повторная обработка;
    * потеря сообщения;
    * долгая доставка события до получателя.
5. 3D files storage
    Хранилище файлов критично для заказов с кастомной 3D-моделью. Проблемы доступа к файлу или задержки чтения напрямую влияют на расчёт стоимости и дальнейшее движение заказа.
6. Shop DB и MES DB
    Базы данных тоже стоит покрыть на уровне database spans, если стек позволяет. Это поможет видеть:
    * медленные запросы;
    * ошибки чтения и записи;
    * точки деградации в транзакциях.
7. Выделенный сервис расчёта стоимости
    В целевой архитектуре расчёт стоимости выносится из MES, его обязательно нужно покрыть трейсингом отдельно.

Обязательные данные для трейсинга

1. trace_id
    Общий идентификатор трассы, чтобы связать весь путь заказа через несколько систем.
2. span_id
    Идентификатор отдельной операции внутри трассы.
3. parent_span_id
    Нужен для восстановления цепочки вызовов.
4. correlation_id
    Сквозной идентификатор бизнес-операции, который передаётся между HTTP-запросами, очередями и фоновыми задачами.
5. order_id
    Ключевой бизнес-идентификатор заказа.
6. source
    Источник заказа:
    * b2c
    * b2b
    * crm_manual
7. service_name
    Название сервиса:
    * shop-api
    * crm-api
    * mes-api
    * price-calculation-service
8. operation_name
    Название операции, например:
    * create_order
    * upload_3d_file
    * calculate_price
    * publish_order_event
    * consume_order_event
    * update_order_status
9. endpoint / route
    Для HTTP-вызовов.
10. http_method
    Например GET, POST.
11. http_status_code
    Для фиксации успешных и ошибочных ответов.
12. message_queue_name / exchange / routing_key
    Для операций через RabbitMQ.
13. message_type
    Например:
    * order_created
    * price_calculated
    * manufacturing_started
14. current_status / next_status
    Для отслеживания переходов заказа по статусам.
15. duration
    Время выполнения операции.
16. result
    Итог операции:
    * success
    * error
    * timeout
    * retry
17. error_type / exception_message
    Если операция завершилась ошибкой.
18. db_statement / db_operation / db_table
    Для database spans, без сохранения чувствительных данных.
19. file_id / file_size / model_complexity_bucket
    Для операций с 3D-файлами и расчётом стоимости.
20. environment
    Например:
    * dev
    * stage
    * prod

Мотивация

Сейчас компания узнаёт о проблемах в заказах в основном через жалобы клиентов, партнёров и операторов. Это означает, что инциденты выявляются слишком поздно — уже после того, как заказ был потерян, завис или сильно просрочен. При этом архитектура системы распределённая: заказ проходит через несколько приложений, базы данных, очередь сообщений и файловое хранилище. Без трейсинга быстро понять, где именно произошёл сбой, практически невозможно.

Обычный мониторинг по метрикам показывает, что “что-то пошло не так”: выросло время ответа, увеличилась очередь, стало больше ошибок. Но он не всегда отвечает на вопрос, какой именно заказ пострадал, на каком шаге это произошло и какая система виновата. Именно эту задачу решает трейсинг.

Внедрение трейсинга даст компании следующие преимущества:

1. Сквозная прозрачность жизненного цикла заказа
    Можно будет увидеть полный путь заказа через Shop API, очередь, CRM API, MES API и другие компоненты.
2. Сокращение времени расследования инцидентов
    Команда сможет быстрее находить точку отказа: очередь, API, файловое хранилище, БД или расчёт стоимости.
3. Уменьшение числа потерянных и зависших заказов
    Трейсинг позволит раньше замечать, где заказ перестал двигаться по процессу.
4. Повышение качества B2B API
    Для партнёров станет проще расследовать случаи, когда заказ был принят, но не дошёл до следующей системы.
5. Основа для оптимизации архитектуры
    Команда сможет принимать решения на основе реальных данных о времени прохождения заказа и узких местах.

Компромиссы

Внедрение трейсинга полезно, но не во всех случаях его стоимость окупается одинаково быстро. Нужно учитывать следующие ограничения.

1. Трейсинг не заменяет мониторинг и логирование
    Он хорошо показывает путь отдельного запроса или заказа, но не заменяет метрики по нагрузке, насыщению и бизнес-SLA.
2. Не все компоненты одинаково легко инструментировать
    Если часть логики находится в проприетарном или слабо управляемом компоненте, его интеграция с OpenTelemetry может потребовать отдельной доработки.
3. Трейсинг может быть дорогим по объёму данных
    Если трассировать абсолютно все запросы и сообщения, объём данных и стоимость хранения могут быстро вырасти. Поэтому потребуется sampling и разумный отбор сценариев.
4. Не все проблемы будут видны на уровне трасс
    Например, если заказ “логически потерялся” из-за ошибки бизнес-правила, а не из-за технического сбоя, трасса не всегда сразу покажет корневую причину.
5. Инструментирование RabbitMQ и фоновых задач сложнее, чем HTTP
    Для полноценной сквозной трассы нужно отдельно заботиться о передаче контекста в сообщениях и асинхронных обработчиках.

Безопасность

Система трейсинга будет содержать чувствительную техническую и частично бизнесовую информацию, поэтому нужно заранее предусмотреть меры защиты.

Меры безопасности

1. Ограничение доступа к Jaeger UI
    * доступ только для сотрудников компании;
    * обязательная аутентификация;
2. Ролевая модель доступа
    * просмотр трасс — только для ролей Support, DevOps, Backend, Tech Lead;
    * ограничение административных функций для узкого круга сотрудников.
3. Сегментация сети
    * Jaeger, OTel Collector и backend трейсинга должны быть доступны только из внутреннего контура;
    * внешнего публичного доступа быть не должно.
4. Шифрование трафика
    * использовать TLS для передачи данных между сервисами, Collector и Jaeger;
    * защищать доступ к UI по HTTPS.
5. Минимизация чувствительных данных в трейсах
    * не отправлять в трейсы персональные данные клиентов;
    * не отправлять содержимое 3D-файлов;
    * не сохранять полный SQL с чувствительными параметрами;
    * вместо этого использовать идентификаторы и обезличенные атрибуты.
6. Аудит доступа
    * логировать доступ к системе трейсинга;
    * фиксировать, кто и когда просматривал трассы.
7. Политика хранения данных
    * ограничить retention;
    * удалять старые трейсы по сроку жизни;
    * не хранить технические данные дольше, чем это нужно для расследования и анализа.
