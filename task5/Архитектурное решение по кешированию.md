### Мотивация

Какие проблемы должно решить кеширование

1. Снизить время загрузки первой страницы MES
    Операторы должны быстро видеть новые заказы, так как от этого зависит их вознаграждение.
2. Снизить нагрузку на MES API и MES DB
    Сейчас каждый запрос на дашборд, вероятно, заново обращается к БД. Кеш позволит сократить количество одинаковых чтений.
3. Улучшить стабильность системы при росте заказов
    При увеличении количества операторов и заказов именно read-нагрузка на MES будет расти быстрее всего.
4. Изолировать пользовательские сценарии от тяжёлых процессов
    MES уже совмещает слишком много обязанностей, включая показ списка заказов и работу со статусами. Кеширование позволит хотя бы частично разгрузить чтение.

Какие элементы системы я предлагаю включить в кеширование

В первую очередь:

* список заказов для MES Dashboard;
* список заказов по статусу;
* первые страницы списков, отсортированные по дате создания/обновления;
* счётчики заказов по статусам.

Во вторую очередь можно рассмотреть:

* карточки недавно открывавшихся заказов;
* справочные данные, которые редко меняются.

### Предлагаемое решение

Для этого кейса я предлагаю внедрить серверное кеширование.

Почему именно серверное, а не клиентское

Клиентское кеширование здесь будет недостаточно эффективно, потому что:

* список заказов — это общие данные для многих операторов;
* заказы активно меняют статус;
* оператору важно видеть достаточно актуальные данные;
* клиентский кеш не уменьшает нагрузку на MES API и БД так сильно, как серверный;
* один и тот же список открывают много пользователей, поэтому общий серверный кеш выгоднее.

Серверное кеширование лучше подходит, потому что:

* оно разгружает БД и API централизованно;
* одним кешем могут пользоваться все операторы;
* проще централизованно управлять инвалидацией;
* можно использовать быстрый in-memory/Redis слой перед БД.

Внедрить:

* Redis как серверный кеш;
* кеширование в MES API;
* кешировать ответы для чтения списка заказов и агрегатов по статусам.


Для MES Dashboard оптимальнее всего использовать Cache-Aside.


Этот паттерн хорошо подходит, потому что:

* сценарий чтения значительно важнее и чаще сценария записи;
* данные можно получать из БД только при cache miss;
* приложение сохраняет контроль над тем, что именно и как кешировать;
* его просто внедрить точечно, без перестройки всей модели данных.

Как это будет работать:

1. MES API получает запрос на список заказов.
2. Сначала проверяет Redis по ключу запроса.
3. Если данные есть — возвращает их из кеша.
4. Если данных нет — читает из БД, формирует ответ, кладёт его в кеш и возвращает пользователю.

Почему не Write-Through

Write-Through хуже подходит, потому что:

* он полезнее там, где нужно сразу писать и в БД, и в кеш;
* в нашем кейсе главная проблема — не запись, а тяжёлое чтение дашборда;
* списки заказов и фильтры — это производные представления, а не одна сущность, которую удобно синхронно записывать в кеш при каждом обновлении;
* обновление большого количества связанных ключей при каждой записи усложнит решение.

Почему не Refresh-Ahead

Refresh-Ahead можно использовать позже как улучшение, но не как основной первый шаг, потому что:

* нужно заранее предсказывать, какие ключи будут востребованы;
* потребуется дополнительная фоновая логика обновления;
* реализация сложнее;
* в начале выгоднее сделать простое и понятное кеширование самых частых запросов.

Что именно кешировать

1. Список заказов для MES Dashboard

Например:

* status = NEW / PRICE_CALCULATED / MANUFACTURING_APPROVED
* сортировка по newest first
* первая страница

2. Счётчики заказов по статусам

Эти данные часто нужны для дашборда и меняются не на каждом миллисекундном интервале.

3. Результаты популярных фильтров

Например:

* новые заказы;
* заказы “готовы к производству”;
* заказы “в работе”.

Стратегия инвалидации кеша

Предлагаю использовать комбинированную стратегию:

* программную инвалидацию по ключу при изменении статуса заказа;
* короткий TTL как защитный механизм.


У заказов есть понятные события, после которых данные становятся неактуальными:

* смена статуса;
* назначение заказа оператору;
* создание нового заказа;
* завершение упаковки или отправки.

Значит, при таких событиях можно программно инвалидировать нужные ключи.

Как именно будет работать инвалидация

При изменении статуса заказа MES API:

1. обновляет запись в БД;
2. определяет, какие кеш-ключи могли затронуться;
3. удаляет эти ключи из Redis;
4. следующий запрос читает свежие данные из БД и заново прогревает кеш.
